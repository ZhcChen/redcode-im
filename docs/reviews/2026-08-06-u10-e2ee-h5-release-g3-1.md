# U10 E2EE H5 G3.1 候选构建与静态发布安全验收

## 结论

G3.1 已完成，独立 security、correctness、reliability 与 testing 复审无未关闭
P0/P1。H5 production-mode 候选构建现在具备严格 CSP、完整 endpoint、source
commit、`bun.lock`、资源摘要、公开 source map 阻断、外置 evidence 和 GitHub OIDC
artifact provenance。

该结论不关闭 U7 P0-4。真实 CDN/Caddy/TLS response headers、浏览器 CSP Console、
WebCrypto、存储、Network、日志和运行时 fail-closed 场景属于 G3.2；生产 E2EE 继续
保持 **No-Go**。

## 实现边界

- `make h5-app.release.build` 要求干净工作区、HTTPS API 与 WSS URL，构建前后发现
  tracked source 漂移即失败。
- `release-manifest.json` 绑定完整 API/WS URL、当前 Git commit、`h5-app/bun.lock`
  SHA-256、9 项 response header policy 和全部候选资源摘要。
- CSP 禁止通用 `unsafe-inline` / `unsafe-eval`，仅保留 WebAssembly 所需的
  `'wasm-unsafe-eval'`；Vue 动态 inline style 已改为有限静态 class。
- `release-manifest.json` 与 `security-headers.json` 不由 hardened server 对外提供；
  本地 evidence 位于 deployable `dist` 外。
- GitHub release workflow 使用固定 SHA 的 `actions/attest-build-provenance` 和 OIDC
  对最终 H5 tarball 签发 provenance；`publish-release` 显式依赖该 job。
- 手工 release 会验证已有 tag commit 等于 `GITHUB_SHA`，新 tag 显式以
  `--target GITHUB_SHA` 创建。

## G3.2 输入

1. 配置隔离候选域名和真实 HTTPS/WSS endpoint，不复用 dev server 作为发布证据。
2. 用真实浏览器检查 response headers、TLS、CSP violation、Console、Network、
