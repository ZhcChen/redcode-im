# PRD-002: Backend Rust 代码测试覆盖率 100% 目标

## 1. 需求背景

当前 Backend Rust 代码测试覆盖率仅 **12.42%**（3,675/29,598 行），距离工业级标准（70-80%）和高质量目标（100%）差距较大。

### 覆盖率现状

| 模块分类 | 代表文件 | 当前覆盖率 | 行数 |
|---------|---------|-----------|------|
| Admin Handlers | `handlers/admin.rs` | 0% | 3,533 |
| Version Handlers | `handlers/version.rs` | 0% | 1,126 |
| Group Handlers | `handlers/group_management.rs` | 0% | 882 |
| WebSocket | `websocket/protocol.rs` | 0% | 453 |
| Redis Session | `redis/session.rs` | 0% | 376 |
| Database Stores | 多个 store 文件 | 0% | ~5,000+ |
| Auth Handlers | `handlers/auth.rs` | 部分 | ~800 |
| User Handlers | `handlers/user.rs` | 部分 | ~600 |

### 测试覆盖分布

- **Go 集成测试**：252 个路由 100% 覆盖（黑盒 API 层面）
- **Rust 单元测试**：仅 5 个路由覆盖（白盒代码层面）
- **差距**：Go 测试不计入 `cargo llvm-cov` 覆盖率统计

## 2. 目标与范围

### 目标

- **最终目标**：Backend Rust 代码测试覆盖率达到 **100%**
- **分阶段里程碑**：
  | 阶段 | 目标覆盖率 | 主要内容 |
  |------|-----------|---------|
  | Phase 1 | 30% | 核心业务路径（PRD-001 范围） |
  | Phase 2 | 50% | 扩展 API + 核心 Services |
  | Phase 3 | 70% | Admin API + WebSocket |
  | Phase 4 | 90% | Database Stores + Utils |
  | Phase 5 | 100% | 边界条件 + 错误路径补全 |

### 范围

- **包含**：
  - `backend/src/handlers/` - 所有 HTTP Handler
  - `backend/src/database/` - 所有数据存储层
  - `backend/src/services/` - 所有业务服务层
  - `backend/src/websocket/` - WebSocket 协议处理
  - `backend/src/redis/` - Redis 会话/缓存
  - `backend/src/auth/` - 认证授权模块
  - `backend/src/utils/` - 工具函数

- **不包含**：
  - E2E 测试（Patrol/Playwright）
  - 第三方集成测试（COS、推送服务）
  - 生成代码（`src/generated/`）

## 3. 用户画像与场景

| 用户 | 场景 | 期望 |
|------|------|------|
| 开发者 | 重构代码时确保不破坏现有功能 | 100% 覆盖率提供完整回归保护 |
| 审查者 | Code Review 时评估代码质量 | 高覆盖率证明代码经过充分验证 |
| 运维 | 发版前验证系统稳定性 | 覆盖率报告作为发布检查项 |
| 管理者 | 评估项目质量指标 | 覆盖率作为技术债务指标 |

## 4. 关键流程

```
分析当前覆盖率 → 识别未覆盖模块 → 按优先级排序 → 分阶段编写测试 → 验证覆盖率提升 → 集成 CI/CD
```

## 5. 业务规则与约束

1. **测试语言**：Rust 单元测试（计入 llvm-cov 覆盖率）
2. **测试框架**：`tokio::test` + `axum::test` + `tower::ServiceExt`
3. **测试隔离**：每个测试独立创建测试用户/数据
4. **测试栈**：使用 `tests/docker-compose.yml` 提供 PostgreSQL/Redis
5. **覆盖率工具**：`cargo llvm-cov` 生成报告
6. **CI 集成**：覆盖率报告纳入 CI/CD 流程

## 8. 非功能需求

- **性能**：单个测试用例执行 < 5 秒
- **可维护性**：测试代码遵循 DRY 原则，复用 `tests/api/common.rs` fixtures
- **可重复性**：测试结果稳定，无 flaky tests
- **并行执行**：测试可并行运行（数据隔离）
- **CI 集成**：覆盖率报告自动生成并归档

- 不编写 E2E 测试（属于另一个 PRD 范畴）
- 不测试第三方 SDK 内部逻辑（如 COS SDK）
- 不为了覆盖率而编写无意义测试
- 不破坏现有测试用例

## 11. 开放问题

1. **覆盖率阈值**：CI/CD 是否设置最低覆盖率门槛？建议：每次 PR 不降低覆盖率
2. **Mock 策略**：外部依赖（COS、推送）如何 Mock？建议：trait 抽象 + mock 实现
3. **测试数据**：是否需要 fixtures 文件？建议：代码生成，避免硬编码

## 13. 风险与依赖

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 部分 Handler 依赖外部服务 | 无法本地测试 | 使用 Mock 或 trait 抽象 |
| 测试数据污染 | 测试不稳定 | 每个测试独立创建/清理数据 |
| 测试执行时间过长 | CI 效率降低 | 并行执行 + 合理分组 |
| 历史代码难以测试 | 覆盖率提升困难 | 必要时小范围重构 |

## 16. 术语表

- **覆盖率**：测试执行时覆盖的代码行数占总行数的比例
- **llvm-cov**：Rust 覆盖率工具，基于 LLVM 编译器
- **Phase**：里程碑阶段
- **Mock**：模拟对象，用于替代真实依赖
