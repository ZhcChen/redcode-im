# PRD-001: Backend Rust 代码测试覆盖完善

## 1. 需求背景

当前 Backend Rust 代码测试覆盖率仅 **12.42%**（行覆盖率），大量核心模块缺乏测试保护：
- `handlers/admin.rs` - 0%（3533 行）
- `handlers/version.rs` - 0%（1126 行）
- `handlers/group_management.rs` - 0%（882 行）
- `websocket/protocol.rs` - 0%（453 行）
- `redis/session.rs` - 0%（376 行）
- 多个 database stores - 0%

API 路由层面：Go 测试已覆盖 100%（252 个路由），Rust 测试仅覆盖 5 个路由。

根据 CLAUDE.md 规范，**所有测试除非特殊指定否则使用 Go**，因此本次覆盖完善主要通过 Go 集成测试实现，辅以 Rust 单元测试补充纯逻辑验证。

## 2. 目标与范围

### 目标
- 提升 Backend 整体测试覆盖率至 **30%** 以上（阶段性目标）
- 覆盖核心业务路径与边界条件
- 建立可持续的测试补充机制

### 范围
- **包含**：handlers、database stores、services 层测试
- **不包含**：E2E 测试、前端测试、第三方集成测试

## 3. 用户画像与场景

| 用户 | 场景 | 期望 |
|------|------|------|
| 开发者 | 提交代码后运行回归测试 | 快速发现引入的缺陷 |
| 审查者 | Code Review 时检查测试覆盖 | 确保关键路径有测试保护 |
| 运维 | 发版前验证系统稳定性 | 测试全部通过才能上线 |

## 4. 关键流程

```
识别未覆盖模块 → 设计测试用例 → 编写测试代码 → 运行验证 → 更新覆盖率报告
```

## 5. 业务规则与约束

1. **语言选择**：Go 优先（黑盒 API 测试），Rust 补充（白盒单元测试）
2. **测试隔离**：测试之间互不影响，可并行执行
3. **数据清理**：测试结束后不残留脏数据
4. **依赖管理**：使用测试栈（`tests/docker-compose.yml`）提供 PostgreSQL/Redis

## 6. 功能列表

| 功能 | 描述 | 优先级 |
|------|------|--------|
| Health API 测试 | 覆盖 `/healthz`、`/readyz` 端点 | P0 |
| Settings API 测试 | 覆盖公开设置读取接口 | P0 |
| User API 测试增强 | 覆盖用户信息更新、密码修改、搜索 | P1 |

## 7. 功能详情

### 7.1 Health API 测试
- **描述**：验证健康检查端点正常工作
- **用户故事**：作为运维，我想要通过 `/readyz` 检查服务就绪状态，以便配置 K8s 探针
- **验收标准**：
  - [ ] `GET /healthz` 返回 200 OK
  - [ ] `GET /readyz` 返回 200 OK 及组件状态 JSON
  - [ ] 数据库/Redis 不可用时返回 503
- **成功/失败边界**：
  - 成功条件：所有组件状态为 "ok"
  - 失败条件：任一组件状态为 "error"

### 7.2 Settings API 测试
- **描述**：验证公开设置接口
- **用户故事**：作为客户端，我想要获取应用配置（如验证码开关），以便正确展示登录界面
- **验收标准**：
  - [ ] `GET /settings/general` 返回应用名称
  - [ ] `GET /settings/captcha` 返回验证码配置
  - [ ] `GET /settings/privacy-policy` 返回隐私协议
  - [ ] `GET /settings/user-agreement` 返回用户协议
- **成功/失败边界**：
  - 成功条件：返回有效 JSON 结构
  - 失败条件：返回 5xx 错误

### 7.3 User API 测试增强
- **描述**：补充用户相关接口测试
- **验收标准**：
  - [ ] `PATCH /users/me` 更新昵称成功
  - [ ] `POST /users/me/password` 修改密码成功
  - [ ] `GET /users/search` 搜索用户返回结果
  - [ ] `GET /users/{id}` 获取指定用户信息
  - [ ] `DELETE /users/me` 注销账号成功

### 7.4 Friend API 测试增强
- **描述**：补充好友相关接口测试
- **验收标准**：
  - [ ] `POST /friends/requests` 发送好友申请
  - [ ] `POST /friends/requests/{id}/respond` 接受/拒绝申请
  - [ ] `GET /friends` 获取好友列表
  - [ ] `PATCH /friends/{id}/remark` 修改好友备注
  - [ ] `DELETE /friends/{id}` 删除好友

### 7.5 Database Stores 单元测试
- **描述**：为覆盖率为 0% 的 store 添加单元测试
- **验收标准**：
  - [ ] `settings_store` 测试
  - [ ] `document_store` 测试
  - [ ] `account_store` 基础测试

## 8. 非功能需求

- **性能**：单个测试用例执行时间 < 5 秒
- **可维护性**：测试代码遵循项目规范，使用 testutil fixtures
- **可重复性**：测试可多次运行，结果一致

## 9. 版本规划

- **MVP**：Health + Settings API 测试（覆盖 P0）
- **V1**：User + Friend API 测试增强（覆盖 P1）
- **V2**：Database Stores 单元测试（覆盖 P2）

## 10. 不做什么

- 不编写 E2E 测试（Patrol/Playwright）
- 不测试第三方集成（COS、推送服务）
- 不重构现有测试代码
