# feat: 对齐 API、Flutter 与 IM UI 能力

## 目标

建立 API、Flutter App 与 `im-ui-html` 设计源之间可验证的能力映射，并按风险分批消除不一致：

- 管理后台的消息加密选项真实控制客户端发送模式和服务端接收约束。
- API 已有能力在 Flutter 中可用，并在 HTML 设计源中有对应入口、状态和交互。
- UI 已设计但 API 尚未提供的能力有明确边界，不再被误判为已完成。
- SMS 登录和短信重置密码保留 API 现状，本计划不改 App/UI。

本计划是消息运行模式第二阶段与 IM 2.0 UI 对齐工作的共同执行入口，不改写上述文档的历史结论。

## 范围

### 本计划覆盖

- 维护 API / Flutter / HTML 三方能力矩阵。
- 复用 `content_audit_mode=plaintext|e2ee` 作为全局消息加密发送开关。
- 完成客户端密钥生命周期、加密发送、接收解密、失败状态和兼容策略。
- 服务端按运行模式约束明文与密文发送端点，防止配置与实际行为脱节。
- 在 HTML 设计源补齐 API/Flutter 已有的消息、会话、好友、群治理、举报反馈、贴纸和版本交互。
- 对 Flutter 尚未接入但 API 已具备的能力补齐真实调用和验收。

### 本计划不覆盖

- SMS 登录、短信重置密码的 App/UI 接入。
- 为朋友圈、音视频通话、扫一扫、附近的人、游戏新建后端能力。
- 把联系人名片、收藏内容升级为服务端结构化消息类型。
- 用 HTML 原型直接连接真实 API。
- 修改 `server_storage_mode` 的既有语义。

## 加密发送关键决策

> U10 的当前实施事实源为 `docs/plans/2026-08-04-001-feat-u10-e2ee-release-gate-plan.md`。本节保留早期范围与决策背景；协议选型、Go/No-Go、文件边界和验收门禁以 U10 专项计划为准。

1. **全局强制模式**：后台选择 `e2ee` 后，服务端拒绝普通明文发送端点；选择 `plaintext` 后，服务端拒绝加密发送端点，避免客户端绕过后台策略。
2. **禁止静默降级**：E2EE 模式下缺少密钥、加密失败或客户端版本不支持时，发送失败并给出可恢复提示，不允许自动改发明文。
3. **历史兼容**：历史明文与新密文可共存；渲染依据消息的 `encrypted_content` / `encryption_metadata`，而不是用当前全局开关推断历史消息格式。
4. **密钥边界**：每台设备使用独立身份密钥和预密钥；私钥只保存在平台安全存储，服务端只保存公开 key bundle。
5. **会话范围**：先完成单聊、多设备的端到端闭环，再设计群聊 sender-key 分发；群聊不允许用“每条消息共享同一服务端密钥”的临时方案。
6. **协议实现**：优先采用经过审计、Flutter 可维护的 Signal Protocol 实现；在依赖、许可证、平台支持和互操作测试通过前，不自行设计密码协议。
7. **模式切换**：客户端每次发送前使用已缓存配置并做短周期刷新；服务端是最终裁决者。服务端返回模式冲突后，客户端刷新配置并保留待发送草稿。
8. **组合语义**：`persist + e2ee` 保存密文；`relay_only + e2ee` 仅转发密文；两种模式都不让服务端获得明文。

## 阶段拆分

### 阶段 1：契约与证据基线

- 建立可追踪的能力矩阵，标注 API 路由、Flutter 调用和 HTML 页面。
- 为明文/密文发送端点增加运行模式强制约束和合同测试。
- 把 Admin 文案从“审计模式”调整为用户可理解的“加密发送”，同时保留底层枚举。

### 阶段 2：客户端 E2EE 单聊闭环

- 选型并验证 Signal Protocol Flutter 实现。
- 实现设备密钥生成、安全存储、bundle 发布/获取和会话建立。
- 实现文本消息加密发送、WebSocket/历史消息解密、密钥缺失和身份变化状态。
- 覆盖旧明文、新密文共存及模式切换。

### 阶段 3：E2EE 多设备与群聊

- 完成同一用户多设备 key bundle 与发送扇出。
- 采用 sender-key 或所选协议的标准群聊机制完成群密钥分发、成员变更和轮换。
- 覆盖设备撤销、群成员加入/退出和无法解密后的恢复路径。

### 阶段 4：API 已有能力的 UI 对齐

- 补齐消息与会话管理设计。
- 补齐好友危险操作和群治理设计。
- 补齐举报、反馈、贴纸、账号和版本状态。
- 对矩阵中 Flutter 的真实缺口实施 API 接入，不重复实现已有能力。

### 阶段 5：全量验收与收口

- 逐项验证 API 合同、Flutter 行为和 HTML 设计映射。
- 将 UI 有/API 无的能力迁出为独立后端产品计划。
- 进入 `review`，沉淀 E2EE 运维、模式切换和故障排查文档。

## 执行单元

### U1：能力矩阵事实核对

- 涉及：`api/src/routes.rs`、`app/lib/`、`im-ui-html/`、`docs/reviews/`
- 完成标准：每项能力都有路由、调用点、页面和状态四类证据；缺失项明确责任模块。
- 验证：`rg`、定向源码阅读；跨模块调用链不明确时才手工使用 CRG。

### U2：加密模式服务端强制与 Admin 语义

- 涉及：`api/src/handlers/message.rs`、`api/src/services/message_runtime.rs`、API 合同测试、Admin 通用设置页。
- 完成标准：两个发送端点按模式互斥；错误码可被客户端识别；后台显示明确开关、影响范围和保存反馈。
- 验证：`make api.test`、Admin 类型检查与页面手工验证。

### U3：E2EE 技术选型验证

- 涉及：Flutter 依赖、最小互操作测试、密钥存储适配。
- 完成标准：确认协议库许可证、Android/iOS 支持、密钥序列化、单聊和群聊能力；形成 Go/No-Go 结论。
- 验证：隔离 PoC 测试，不接入正式发送链路前先验证双端加解密。

### U4：Flutter 单聊 E2EE

- 涉及：认证后的设备初始化、key API、`MessageService`、WebSocket、消息模型、本地安全存储和聊天 UI。
- 完成标准：两台设备可交换密文并在端侧解密；服务端和数据库不可得到明文；失败不降级。
- 验证：Flutter 单元测试、integration test、API 数据库检查和真机/Simulator 联调。

### U5：Flutter 多设备与群聊 E2EE

- 涉及：设备列表、bundle 扇出、群密钥分发、成员变更、密钥轮换。
- 完成标准：多设备及群聊场景不丢收件人；移除成员后无法解密后续消息。
- 验证：至少三设备、三成员自动化场景与人工联调。

### U6：消息、会话与好友 UI 对齐

- 涉及：`im-ui-html` 消息菜单、已读详情、归档列表、好友详情；必要时补 Flutter 缺口。
- 完成标准：API 已有操作在设计源中具备正常、禁用、失败和确认状态。
- 验证：设计源路由巡检、移动/桌面截图和 Flutter 定向测试。

### U7：群治理 UI 对齐

- 涉及：群设置、管理员、入群申请、禁言、规则、转让、解散、操作日志。
- 完成标准：按角色显示可执行动作，危险操作有二次确认，状态与 API 权限一致。
- 验证：设计源角色场景巡检与 Flutter/API 合同测试。

### U8：外围 API 能力 UI 对齐

- 涉及：举报、反馈、贴纸、头像、注销、版本和热更新。
- 完成标准：矩阵中 API 已有项均有真实 App 入口或明确不适用结论，HTML 同步表达关键状态。
- 验证：模块测试、页面巡检和错误状态检查。

### U9：验收与文档收口

- 涉及：能力矩阵、测试索引、架构参考、独立后端待办计划。
- 完成标准：无“UI 看似可用但 API 不存在”或“API 已有但无入口且无结论”的未标注项。

## 建议执行顺序

1. U1 -> U2，先固定事实和服务端安全边界。
2. U3 通过后执行 U4；U3 不通过时停止 E2EE 主链路改造并重新选型。
3. U4 验收后执行 U5，避免同时调试单聊与群聊协议。
4. U6、U7、U8 可在 E2EE 协议稳定后按独立业务闭环推进。
5. U2、U4、U5、U8 完成后分别进入一次定向 `review`；最后执行 U9 全量审查。

## 验证方式

```bash
git diff --check
make api.test
cd admin && npm run type:check
cd app && flutter test
```

- App 联调按仓库设备优先级执行，并在真机测试前重新探测本机局域网 IP。
- HTML 设计源使用单一浏览器会话检查移动和桌面视口、路由、弹层、禁用和错误状态。
- E2EE 验收额外检查数据库、日志、Push payload 和 WebSocket 帧中不存在消息明文。

## 风险与阻断条件

- 现有加密端点只接受调用方提供的密文，不等于已具备完整 E2EE。
- 协议库若不支持 Flutter 当前目标平台、多设备或群聊，不得以自制算法临时替代。
- 全局切到 E2EE 会让旧客户端无法发送；上线前必须具备客户端最低版本门槛或灰度机制。
- Push 预览、引用摘要、搜索、内容审核、举报取证会受 E2EE 影响，必须逐项定义产品降级。
- 群聊密钥轮换和设备撤销遗漏会造成已移除成员继续读取后续消息，是 U5 的阻断级验收项。

## 提交边界

- 计划/矩阵文档单独提交。
- API 强制约束与合同测试单独提交。
- Admin 开关语义与页面验证单独提交。
- E2EE 依赖/PoC、单聊、多设备群聊分别提交。
- 各 UI 能力按消息会话、群治理、外围设置拆分提交。
