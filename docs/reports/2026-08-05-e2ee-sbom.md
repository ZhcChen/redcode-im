# U10 E2EE U7-C 六端 SBOM、许可证与漏洞门禁报告

## 结论

U7 P0-3 的实现与 CI 门禁已完成：API、E2EE core、Android、iOS、H5、Admin
六端均从提交入库的 lockfile 生成 CycloneDX 1.5 SBOM，并通过固定版本
OSV-Scanner、SwiftURL 查询、许可证策略和限时精确例外统一裁决。

CI run `31032243630` 对 commit `e6287df1` 执行 23 个正负夹具、六端扫描、
report/SBOM/lockfile identity 三方完整性校验、commit 绑定和 artifact 上传，最终
通过：29 个精确限时例外，0 个未处理阻断项。

这里的 `pass` 不表示“零 advisory”。E2EE core 仍有 OpenMLS 0.8.1 固定依赖导致
的限时风险接受，统一在 2026-09-05 到期；到期、未命中或字段缺失会自动阻断。
生产 E2EE 仍为 **No-Go**，因为 U7 P0-4 H5 发布安全尚未关闭。

## 例外与剩余风险

CI 接受 10 个 vulnerability finding 和 19 个逐包许可证 finding，全部 owner 为
`ZhcChen`，到期日为 2026-09-05。

漏洞例外分为：

- API `rsa 0.9.10 / RUSTSEC-2023-0071`：lockfile 中存在，但当前
  `jsonwebtoken 10.4.0` 使用 `aws_lc_rs`；`cargo tree --target all -i rsa@0.9.10`
  不可达。
- `libcrux-aesgcm 0.0.7` 与 `libcrux-chacha20poly1305 0.0.7`：来自未启用的
  `hpke-rs-libcrux` optional 分支，当前 feature 图不可达。
- `instant 0.1.13`：OpenMLS 0.8.1 的 wasm timer 固定依赖，当前稳定依赖范围无
  修复版本。
- `libcrux-secrets 0.0.5`、`libcrux-sha3 0.0.8`：当前
  `openmls_rust_crypto -> hpke-rs 0.6.1` feature 图可达；上游分别已在 0.0.6、
  0.0.10 修复，但 hpke-rs 0.6.1 固定兼容范围无法直接升级。OpenMLS 最新版仍为
  `0.9.0-rc.1`，本轮不以 RC 升级替代稳定发布门禁。这三项是明确的限时风险接受，
  必须在到期前完成稳定版迁移或重新裁决。
- `proc-macro-error2 2.0.1`：当前普通 feature 图不可达，仅属于上游构建宏链。

许可证例外覆盖 JNA 双许可证的 Apache 分支，以及逐包复核的 BlueOak、CC0、
CC-BY、CDLA-Permissive、Python-2.0 和扫描元数据缺失但包内 LICENSE 为 MIT 的
依赖。例外不跳过扫描，版本或 finding 变化后不会自动继承。

## Fail-Closed 证据

23 个隔离场景覆盖：

- 正常报告和受信 gate / 独立 source checkout；
- high/critical、未知严重度、拒绝许可证；
- 过期、缺 owner、wildcard、unused exception；
- scanner 不可用、漏洞数据库/下载失败、scanner exit 1；
- 截断 JSON、缺 report、缺/空/错误版本 SBOM；
- report/SBOM 不一致，以及二者同步截断但未完整覆盖 lockfile；
- 敏感 marker 泄漏。

扫描失败时不上传可能含敏感内容的 artifact。成功 artifact 才进入 30/90 天留存；
release publish 只下载 Android/API 构建 artifact，不会把供应链 evidence 混入正式
GitHub Release 资产。
