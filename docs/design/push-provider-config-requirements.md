# Push 云平台配置后台化需求（Admin）

## 1. 背景

Push（系统通知/离线推送）依赖第三方云平台（例如 FCM、APNs 等）的凭据与工程能力配置。当前希望做到：

- **所有需要配置的三方平台凭据**，统一由 **Admin 管理后台可视化配置与维护**；
- **未配置任何平台凭据时**，系统默认仅提供“应用存活时的消息推送能力”（例如 WebSocket 实时推送），不发送系统通知；
- 后续可按里程碑逐步接入更多平台，不影响主流程稳定性。

> 说明：这里的“应用存活时才会推送”指 **实时推送（WebSocket）**；与“离线推送（系统通知）”概念不同，本文将明确区分两者。

## 2. 术语与边界

- **实时推送（Online Push）**：应用进程存活时，通过 WebSocket 等实时通道把事件推给客户端（不依赖 FCM/APNs）。
- **离线推送 / 系统通知（Offline Push）**：应用不在前台或未运行时，依赖 FCM/APNs 等平台能力产生系统通知（依赖平台凭据与工程配置）。
- **Push 平台**：可选的第三方推送服务提供方（FCM、APNs、各厂商推送、Web Push 等）。

## 3. 目标（必须满足）

1. **配置后台化**：Push 平台配置项不再依赖部署环境变量，由 Admin 后台录入/更新/禁用。
2. **无配置安全降级**：未配置任何 Push 平台时：
   - 业务流程不报错（发消息/转发等不能被推送阻塞）；
   - 仅保留实时推送能力（应用存活时可收到消息/事件）。
3. **可观测与可运维**：
   - 后台可查看当前启用的平台与最后更新时间/更新人；
   - 支持“发送测试通知”以验证配置有效性（不影响真实业务流量）。
4. **安全合规**：
   - 凭据需加密存储、脱敏展示；
   - 严禁在日志/接口返回中泄露完整密钥或 token。

## 4. 非目标（本阶段不做/可后续）

- 不在本阶段做复杂灰度（按版本/百分比/人群）与多级通知策略（静默、聚合、时段免打扰等）。
- 不在本阶段实现完整的“消息预览摘要/敏感信息屏蔽策略”产品能力（可后续补充）。

## 5. 功能需求

### 5.1 Admin 管理后台（可视化配置）

新增页面：`系统设置 -> Push`（命名可调整）。

页面能力：
- **全局开关**：
  - `Push 总开关（enabled）`
  - `PUSH_SKIP_IF_ONLINE` 类策略（可视化开关：用户在线时是否跳过系统通知）
- **平台配置卡片（按平台/环境）**：
  - 支持 `启用/禁用`
  - 支持 `编辑/保存`
  - 支持 `测试发送`（选择目标 user_id 或输入 device_token）
  - 展示 `updated_at / updated_by`，以及“配置有效性”状态（由测试结果或校验推断）
- **凭据处理**：
  - 仅允许查看脱敏信息（例如只显示末尾 4 位或 hash）
  - 支持轮换：更新凭据后立即生效

建议首批平台（优先级从高到低）：
1. **FCM（Android/iOS 统一入口）**
2. **APNs（iOS 直连，可后续）**
3. 厂商推送（华为/小米/OPPO/vivo，按业务需要再开）
4. Web Push（若 Web 端需要）

### 5.2 后端（配置存储 + API + 运行时加载）

#### 5.2.1 配置存储

建议独立存储（示例概念，最终以实现为准）：
- 表：`push_provider_configs`
  - `provider`：`fcm/apns/...`
  - `platform`：`android/ios/web/...`
  - `env`：`dev/staging/prod`（或与现有环境体系对齐）
  - `enabled`：是否启用
  - `config_public`：可公开展示的配置（非敏感）
  - `config_secret_encrypted`：敏感配置（加密后存储）
  - `updated_at / updated_by`

敏感字段（例如 FCM service account JSON、APNs `.p8` 私钥）必须：
- **加密后落库**
- **永不明文回传给前端**

#### 5.2.2 Admin API（示例）

- `GET /api/admin/push/providers`：查询配置（脱敏）
- `PUT /api/admin/push/providers/{id}`：更新配置（含启用/禁用）
- `POST /api/admin/push/test`：发送测试通知（返回投递结果与错误原因）

#### 5.2.3 运行时行为与降级

- **发送链路永不阻塞主流程**：
  - 业务事件（例如消息发送成功）→ 异步触发 push 发送任务；
  - push 失败仅记录日志/可观测数据，不影响 API 返回成功。
- **无配置时默认降级**：
  - 若未启用任何平台配置，则不做离线推送（系统通知），仅依赖实时推送；
  - 禁止因“配置缺失”导致 panic 或 HTTP 500。
- **设备 token 注册策略**：
  - 允许客户端在未配置平台时仍注册 token（为后续启用做准备）；
  - 后端发送时按“平台是否启用 + token 是否有效”决定是否投递。

### 5.3 客户端（降级策略）

客户端需要满足：
- **没有 Firebase/APNs 配置时，应用仍可正常运行**（不崩溃、不阻塞登录/聊天）。
- 当平台配置齐备时：
  - 正常获取 token；
  - 登录后注册设备、登出注销；
  - 点击通知可跳转到对应会话（可选定位到 message_id）。

## 6. 验收标准（DoD）

1. 未配置任何 Push 平台：
   - 发消息/转发消息等接口不受影响；
   - 客户端在应用存活时仍可通过 WebSocket 收到消息；
   - 不产生系统通知（离线推送）。
2. 配置并启用 FCM：
   - Admin 可通过“测试发送”验证配置有效；
   - 用户离线时可收到系统通知；用户在线时可按策略跳过系统通知。
3. 安全：
   - 管理后台页面与接口不返回明文敏感信息；
   - 后端日志不打印完整密钥/完整 token。

## 7. 实施里程碑（建议）

1. **阶段 A：配置后台化（不改现有发送逻辑）**
   - 增加配置存储与 Admin UI + API；
   - push 发送逻辑仍可临时保留 env 方式（仅开发环境），但生产以后台配置为准。
2. **阶段 B：发送逻辑完全切到后台配置**
   - Push Service 读取 DB 配置并缓存；
   - 支持 FCM（优先）与 APNs（可后续）。
3. **阶段 C：可观测与稳定性**
   - push_logs 落库、失败重试/退避、告警指标等。
