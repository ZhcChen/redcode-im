## 测试步骤

### 步骤 1: 清理环境
1. 完全退出应用
2. 清理浏览器缓存（如果有）
3. 重新启动应用

### 步骤 2: 执行测试
1. 打开应用
2. 输入账号密码或验证码
3. 点击登录
4. **不要进行任何操作，等待 10 秒**
5. 观察是否自动跳回登录页

### 步骤 3: 收集日志
1. 打开浏览器开发者工具（F12）
2. 切换到 Console 标签
3. **完整复制所有日志**（从应用启动到跳转发生）
4. 保存到文本文件

### 步骤 4: 分析日志

按照时间顺序查找以下关键事件：

#### 4.1 查找 Token 被清除的位置
搜索：`[MUTATION_` 且 `新token: 无token`
- 这会告诉我们 token 是在什么时候被清除的
- 查看调用栈，找出是谁调用了 `SET_TOKEN(null)`

#### 4.2 查找触发 Logout 的位置
搜索：`[LOGOUT_` 且 `开始退出登录`
- 查看调用栈，找出是谁触发了 logout
- 可能的触发源：
  - 401 错误处理
  - 用户手动点击退出
  - 其他异常逻辑

#### 4.3 查找 401 错误
搜索：`[401_` 且 `401认证失败`
- 查看是哪个请求返回了 401
- 是否在宽容期内
- 是否触发了自动登出

#### 4.4 查找 Fallback 触发
搜索：`[FALLBACK_` 且 `Fallback 定时器触发`
- 查看是否执行了跳转
- 当时的登录状态是什么

#### 4.5 查找路由守卫拦截
搜索：`[GUARD_` 且 `重定向到登录页`
- 查看是什么路由跳转触发了守卫
- 当时的登录状态是什么

## 关键检查点

1. **Token 设置时机**: 
   - 登录成功后是否立即设置 token？
   - SET_TOKEN 和 SET_USER 的调用顺序是否正确？

2. **登录状态同步**:
   - isLoggedIn 是否与 token 同步更新？
   - 是否存在 token 有值但 isLoggedIn 为 false 的情况？

3. **401 错误来源**:
   - 哪个 API 返回了 401？
   - 是否在宽容期内？
   - 为什么会返回 401？

4. **定时器触发**:
   - Fallback 定时器是否在登录后触发？
   - 触发时的登录状态是否正确？

5. **调用栈分析**:
   - 谁调用了 SET_TOKEN(null)？
   - 谁触发了 logout？
   - 调用链路是什么？
